# SocialKit expansion: platform support and architecture

**Research snapshot: 2026-11-08.** This is a platform feasibility brief for a native Swift SDK. Platform API access is conditional: an SDK cannot confer API product access, app review approval, account eligibility, or permission grants. Recheck provider docs and console requirements before shipping each adapter.

## Recommendation

Model SocialKit as a native client SDK with explicit per-platform capabilities and authorization state. Start with **X**, then **Threads**, then **Instagram professional accounts**, followed by **Facebook Pages** and **LinkedIn**. X has a clear user-authorized write endpoint and OAuth 2.0 PKCE path. Threads shares Meta infrastructure but requires its own user authorization, permissions and app review. Instagram and Pages add more account, Page-task and review dependencies. LinkedIn member posting is comparatively direct once the app has the relevant product access; organization publishing has a separate gated access and role path.

Treat “publish text” and “publish media” as separate capability flags. Do not promise one normalized post shape across platforms: media, account type, destination, review state, post limits and API versions differ. Expose unsupported and approval-dependent operations explicitly rather than emulating them through private APIs or UI automation.

For an initial release, prioritize read-back of the caller's own posts and public count metrics where available. LinkedIn member read access and Meta insights permissions are notable review gates; X metric surfaces and Meta metric catalogs can vary by endpoint/account.

## Public SDK versus backend boundary

An iOS/macOS binary is a **public OAuth client**: users can inspect it, so a client secret embedded in it is not secret. Keep authorization-code verifier/state handling in the app where the provider supports PKCE; validate the callback and bind it to the initiating login. Keep user access and refresh tokens in Keychain, scope narrowly, support revocation/disconnect, and never log credentials. Do not ship provider client secrets or backend signing keys.

The SDK may issue authenticated API requests directly when the provider explicitly supports a public-client flow and the operation only needs the user token. Provide a small credential-provider abstraction so applications can instead delegate OAuth, refresh, token exchange, or publishing through their own server. Meta and LinkedIn flows must be verified per product and endpoint: where exchange or refresh needs a confidential app secret, the SDK must call the developer’s backend rather than disguising a client secret as SDK configuration. X’s documented PKCE user flow is the clearest direct-native case.

For a confidential flow, the consuming developer operates the token exchange and holds the app secret. The SDK can use user-scoped credentials issued through that integration.

## Suggested API shape

- Publish discrete capability metadata per platform/account: `text`, `image`, `video`, `carousel`, `document`, `multiImage`, and read/management capabilities only when documented and available.
- Separate capability state into `available`, `requiresUserAuthorization`, `requiresAppReview`, `requiresProviderProductAccess`, `unsupported`, and `unknown`; permission or console approval should not be represented as a compile-time guarantee.
- Return per-destination outcomes, including an `indeterminate` result for requests whose network outcome is unknown. Do not blindly retry a create call after a timeout; reconcile by provider identifiers or ask the caller to resolve ambiguity.
- Keep provider-specific account identifiers, media preparation and version headers visible where hiding them would make failure opaque. Normalize the common lifecycle, not every provider field.
- Build account linking separately from API publishing. A SocialKit app cannot supply app-review approval on behalf of a consuming app.

## Delivery order

1. **X text publishing and OAuth PKCE.** Establish transport, token-store, error, capability and uncertain-outcome conventions. Add media only after upload and post endpoint constraints are modeled.
2. **Threads text publishing.** Reuse shared Meta OAuth primitives only where scopes, endpoints and token types truly match; keep Threads authorization and capability records separate.
3. **Instagram professional feed publishing.** Target Instagram Login first; keep Facebook Login as a separate future auth mode if there is a concrete product need.
4. **Facebook Pages publishing.** Add Page discovery, Page-task checks and Page-token lifecycle after the consumer app has a reviewed Meta app.
5. **LinkedIn member then organization publishing.** Start with member posts; make organization posting an opt-in capability gated on Community Management access and Page role.

## Uncertainties to resolve before implementation

- Meta documentation pages intermittently returned rate limiting during this research. The linked Meta-owned Postman collections and canonical developer docs establish the feature surfaces, but exact current permission names, app-review evidence, token lifetimes, API version and product-specific access must be checked in the Meta developer console for the actual app before coding.
- LinkedIn’s product enrollment and current API version are controlled through the developer app; documentation can establish scopes and tier structure but cannot establish that a new SocialKit app will be approved.
- X API price, quota and product availability can change independently of endpoint syntax. Validate the developer console before promising a cost or rate limit.
- This document does not claim that all listed media formats or scopes are available to every account, app, geography, or provider access tier.
